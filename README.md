# Голосовой ассистент для задач и встреч в MAX

Персональный AI-ассистент, который живёт ботом в мессенджере MAX. Пользователь говорит или
пишет обычным языком — «напомни завтра в 10 позвонить Ивану», «что у меня на этой неделе?»,
«перенеси встречу с Марией на 16:00» — а ассистент разбирает фразу, ведёт календарь и сам
напоминает, когда приходит время.

**Попробовать:** [@se14810056_bot](https://max.ru/se14810056_bot) — бот развёрнут и работает.
Мини-приложение с расписанием открывается внутри чата, адрес сервиса — `https://87.242.86.141.sslip.io`.

Основные сценарии:

- создать задачу, напоминание или встречу голосом либо текстом;
- посмотреть, что запланировано на день, неделю или конкретную дату;
- найти старую запись по смыслу или по словам из названия;
- перенести, переименовать, отметить выполненной, удалить;
- получить предупреждение, если новая встреча пересекается с уже назначенной;
- загрузить готовый календарь из CSV и дальше спрашивать про него;
- получить напоминание в чат в назначенное время, без запроса со стороны пользователя.

| Изменение/удаление/отметка выполненной голосом | ✅ (плюс) | тулы `update_event` / `delete_event` / `complete_event` |
| Обработка конфликтующих встреч | ✅ (плюс) | `find_conflicts`, предупреждение в ответе агента |
| Контекст диалога («А перенеси её на завтра») | ✅ (плюс) | история реплик в `agent/memory.py` |
| Семантический поиск по старым задачам | ✅ (плюс) | эмбеддинги GigaChat + RRF в `common/repository.py` |
| Несколько пользователей | ✅ (плюс) | изоляция по `user_id` MAX на всех уровнях (БД, поиск, напоминания) |
| Интеграция с реальным календарём | ✅ (плюс) | импорт CSV в чат бота, экспорт `.ics` |

Ключевое: календарь, импортированные из CSV события и напоминания лежат в одной таблице
`events`. Нет отдельных механизмов «для импорта» и «для голоса» — любой путь приводит
к одним и тем же записям и одним и тем же тулам.

## Запуск

Нужны Docker и Docker Compose. Всё остальное поднимается контейнерами.

```bash
git clone https://github.com/loginovalx/ai_assiatant.git
cd ai_assiatant

cp .env.example .env
# впишите в .env: MAX_TOKEN, MAX_WEBHOOK_SECRET, GIGACHAT_CREDENTIALS

docker compose up --build
```

Поднимутся семь сервисов: `postgres`, `redis`, `mcp`, `api`, `gpt2giga`, `agent`, `bot`.

Рабочее развёртывание сделано именно так: те же контейнеры плюс Caddy как HTTPS-прокси,
который направляет `/webhook` в бот, остальное — в API, и сам получает сертификат.
Схема базы применяется автоматически при первом старте на пустом томе.

Чтобы MAX доставлял сообщения, нужен публичный HTTPS-адрес на порт бота (8080). Например,
через туннель:

```bash
ngrok http 8080
docker compose exec bot python -m bot.subscribe add https://<ваш-адрес>/webhook
```

Проверить подписку и удалить её:

```bash
docker compose exec bot python -m bot.subscribe list
docker compose exec bot python -m bot.subscribe delete https://<ваш-адрес>/webhook
```

Без MAX агента можно проверить напрямую:

```bash
curl -s localhost:8002/v1/agent/message \
  -H 'Content-Type: application/json' \
  -d '{"user_id":"1","text":"Напомни завтра в 10 позвонить Ивану"}'
```

Документация HTTP API: <http://localhost:8000/docs>, агента — <http://localhost:8002/docs>.

## Голосовой ввод и подтверждение

```text
голосовое сообщение
   ↓  «🎤 Распознаю…»
faster-whisper (или готовая транскрипция от MAX)
   ↓  «⏳ Думаю…»
тот же агент, что и для текста, но с confirm_changes=true
   ↓  изменяющий тул вызывается в режиме dry_run: проверки и поиск пересечений есть,
   │  записи в базу нет
черновик в Redis (pending_confirmation)
   ↓
«Напомню вам записаться к врачу завтра в 11:00.»
[✅ Подтвердить] [✏️ Изменить] [❌ Отмена]
   ↓ подтверждение
настоящий вызов тула → запись в PostgreSQL → «Готово. …»
```

Распознанный текст пользователю не показывается: сообщения вида
`📝 Распознал: …` убраны, промежуточный результат остаётся внутри системы и в логах.

Подтверждение требуется только для изменяющих команд, пришедших **голосом**. Вопросы
(«что у меня завтра?») выполняются сразу — им подтверждать нечего. Текстовые команды
тоже выполняются сразу: опечатку в своём тексте пользователь видит сам.

Кнопки дублируются словами: «да», «подтверждаю», «ок» выполняют черновик, «отмена»
и «нет» его отменяют. Любая другая фраза при висящем черновике считается правкой —
«давай в 12:30», «не к врачу, а к стоматологу» — и бот показывает исправленный вариант
снова с кнопками. Так интерфейс остаётся обычным чатом, а кнопки лишь ускоряют частые
действия: «Что сегодня?», «Что завтра?», «Создать встречу», «Напоминание».

## Календарь

Все записи — строки таблицы `events`: созданные голосом, написанные текстом и загруженные
из CSV. У записи есть тип (`task`, `meeting`, `reminder`), название, исходная фраза
пользователя, время начала и необязательная длительность.

- **Занятость.** Встреча занимает время всегда (по умолчанию час), дело — только если
  длительность названа, напоминание не занимает никогда: это момент времени.
- **Пересечения.** При создании и переносе репозиторий ищет активные записи, чьи интервалы
  пересекаются с новым. Интервалы полуоткрытые: встречи 15:00–16:00 и 16:00–17:00
  не конфликтуют. Пересечение не блокирует сохранение — запись создаётся, а бот
  предупреждает и предлагает перенести.
- **Относительные даты.** «Завтра», «в пятницу», «на следующей неделе» модель считает
  по шпаргалке дат, которая подставляется в промпт при каждом запросе вместе с текущим
  временем и часовым поясом.
- **Час не выдумывается.** Если пользователь назвал только день, тул отказывается создавать
  встречу или напоминание и просит агента уточнить время. Исключение — часть суток:
  «утром» → 09:00, «днём» → 13:00, «вечером» → 19:00, и бот называет подставленный час вслух.
- **Поиск** идёт тремя способами сразу: полнотекстовый, по опечаткам (триграммы) и по смыслу
  (эмбеддинги), результаты объединяются методом Reciprocal Rank Fusion. Без
  `GIGACHAT_CREDENTIALS` работают первые два.

## Импорт CSV

Формат фиксированный, другие таблицы не поддерживаются:

```csv
id,date,time,text
1,2024-01-07,14:45,Подготовить техническое задание
2,2024-01-12,13:45,Отправить договор Ивану
```

Загрузить можно двумя способами: прислать файл боту прямо в чат MAX или через HTTP API —

Для локального примера ниже нужен `API_ALLOW_DEV_USER_ID=true`. В MAX вместо параметра
пользователя передаётся заголовок `X-Max-Init-Data` (см. [мини-приложение](miniapp/README.md)).

```bash
curl -F file=@calendar.csv "http://localhost:8000/v1/events/import?user_id=123"
```

Что происходит при загрузке: проверяются обязательные колонки, формат даты (ГГГГ-ММ-ДД)
и времени (ЧЧ:ММ). Битая строка не отменяет весь файл — остальные загрузятся, а по
проблемным вернётся список ошибок с номерами строк. Строки сохраняются в ту же таблицу
`events` и привязываются к `user_id`, типом `task` с длительностью 60 минут: так
импортированное событие занимает время и участвует в проверке пересечений.

Повторная загрузка того же файла дублей не создаёт — пара (`user_id`, `id` из CSV)
уникальна. Эмбеддинги при импорте не считаются: на тысяче строк это тысяча запросов
к GigaChat. Для поиска по смыслу после импорта выполните пакетную индексацию:

```bash
docker compose exec mcp python -m scripts.index_calendar --user-id 123
# Без Docker:
uv run python -m scripts.index_calendar --user-id 123
```

Индексация обрабатывает до 1000 строк за запуск, объединяет одинаковые тексты и отправляет
не более 16 разных текстов за запрос. Повторный запуск пропускает уже готовые векторы;
сбой провайдера сохраняет исходные события и результаты завершённых пакетов.

Весь файл в промпт LLM не передаётся. Бэкенд сам выбирает из базы нужные события
по датам, и модель видит только их.

## Напоминания

```text
создание (голос, текст или импорт)
   ↓
строка в events: start_at = когда, notified_at = NULL
   ↓
планировщик в боте просыпается раз в 30 секунд
   ↓
один SQL-запрос резервирует наступившие события на пять минут
   ↓
«Напоминание: позвонить Ивану» уходит в MAX
   ↓
после успешной отправки ставится notified_at
```

Источник истины — база, а не память процесса, поэтому перезапуск сервиса напоминания
не теряет. Резервирование использует `FOR UPDATE SKIP LOCKED` и токен владельца;
после падения процесса резерв истечёт и неотправленное событие вернётся в очередь.
При известной ошибке отправки повтор возможен в следующий тик. Если процесс упал
между доставкой MAX и отметкой в базе, возможна повторная доставка.
Кнопки «Готово» и «На час позже» меняют только запись владельца. Перенос времени
сбрасывает отметку отправки, чтобы напоминание пришло в новый срок.

`REMINDER_LOOKBACK_MINUTES` ограничивает «догоняющие» отправки: после долгого простоя
пользователь получит только то, что наступило за последний час. Без этого импорт календаря
с прошлогодними датами завалил бы чат сотней сообщений.

## История работы

**Календарь и данные**

- предупреждение о пересечении встреч: запись сохраняется, пересекающиеся приходят
  в ответе тула, бот предупреждает и не переносит ничего сам;
- необязательная длительность у событий, поле `duration_minutes` и расчёт конца события;
- выгрузка `.ics` использует настоящую длительность вместо фиксированной;
- импорт календаря из CSV: валидация, идемпотентность по `id`, HTTP-эндпоинт
  `POST /v1/events/import` и приём файла прямо в чате;
- массовое удаление `delete_events` одним вызовом вместо цикла, с подтверждением
  и количеством записей (раньше «удали все задачи» упиралось в лимит шагов агента).

**Качество разбора команд**

- длительность встречи спрашивается, а не подставляется молча; «не знаю» → час,
  и бот говорит об этом;
- час не выдумывается: если названа только дата, тул отказывает и просит уточнить время.
  Проверка детерминированная, в коде, потому что правило в промпте модель игнорировала;
- длительность у напоминания больше не теряется молча — такая команда создаёт дело;
- ответы о времени и длительности строятся по полям записи, а не по исходной фразе:
  модель пересказывала фразу пользователя и выдавала несуществующую длительность;
- час в ответе всегда называется цифрами: «напомню завтра днём» без времени — ошибка.

**Голос и интерфейс**

- автоматическая отправка напоминаний: фоновый планировщик, отметка `notified_at`,
  защита от повторов и от лавины после простоя;
- подтверждение голосовых изменений: черновик в Redis, режим `dry_run` у изменяющих
  тулов, кнопки «Подтвердить / Изменить / Отмена» и те же действия словами;
- правка черновика обычной фразой до сохранения;
- убрано сообщение «📝 Распознал: …», остался короткий статус «Распознаю…»;
- развёрнутое приветствие при первом запуске и кнопка загрузки своего календаря.

**Инфраструктура**

- сервис `bot` подключён к общему `docker-compose`, зависимости и переменные окружения;
- российский корневой сертификат в образе и `SSL_CERT_FILE`, иначе `httpx` не достучится
  до MAX API: библиотека игнорирует системное хранилище и использует свой бандл;
- `av<19` — в новой мажорной версии PyAV убрали аргумент, который зовёт `faster-whisper`,
  и распознавание падало на каждом файле;
- миграции `002_event_duration.sql` и `003_notifications_and_import.sql`;
- тесты SQL и контекста на настоящих Postgres и Redis.

**Доработки по результатам живого тестирования**

- массовое удаление всегда идёт через подтверждение с замороженным снимком ID: раньше
  модель пересказывала пользователю служебный текст ошибки тула, а на «да» удаляла всё
  подходящее на тот момент, а не то количество, которое человек видел в вопросе;
- ответ на уточняющий вопрос («Во сколько?» → «В 13:00») доклеивается к `user_text`
  кодом, а не по инструкции в промпте: модель регулярно теряла названное время;
- выполненные записи не попадают в ответ на «что у меня сегодня» (параметр `include_done`
  у `get_events`), но остаются видимыми в мини-приложении с отметкой;
- мини-приложение: `location.origin` в вебвью MAX может быть строкой `"null"`,
  `AbortSignal.timeout` не поддерживается тамошним WebKit, а бесплатный ngrok отвечал
  на `fetch` своей HTML-заглушкой вместо проксирования — все три случая закрыты;
- подписка на `message_callback` в вебхуке: без неё кнопки отрисовывались, но нажатия
  не доходили до бота.

## Ограничения

Это хакатонный прототип, и о его границах честнее сказать прямо:

- повторяющиеся события (каждый понедельник) не поддерживаются;
- часовой пояс один на всю систему, индивидуального для пользователя нет;
- несколько голосовых изменений нужно отправлять отдельными командами для подтверждения;
- для поиска по смыслу после импорта CSV требуется пакетная индексация;
- кнопки MAX проверены по документации Bot API, но вживую — только в одном окружении.

## Размещение мини-приложения и обновление базы

`docker compose up --build -d` запускает миграции до API/MCP. Существующие данные
сохраняются; версия схемы хранится в `schema_migrations`. Для запуска без Compose:

```bash
uv run python -m scripts.migrate
```

Страница мини-приложения раздаётся API на `/app/`, с проверкой подписанных данных MAX.
`API_ALLOW_DEV_USER_ID=false` включён по умолчанию. Инструкция — в
[miniapp/README.md](miniapp/README.md). Порты Compose доступны только через localhost;
публичный HTTPS-прокси должен направлять `/app/` и `/v1/` в API, `/webhook` в бот.
Внутренние MCP, агент, PostgreSQL, Redis и прокси GigaChat публиковать не требуется.
