# Бэкенд: БД, MCP-сервер, HTTP API

Владелец: A (Алексей). Здесь всё, что нужно агенту (C), Mini App (D) и презентации (F).

## Запуск

```bash
cp .env.example .env          # GIGACHAT_CREDENTIALS можно оставить пустым
docker compose up --build     # postgres, valkey, mcp :8001, api :8000
```

Проверка: `curl localhost:8001/health`, `curl localhost:8000/health`, документация API — http://localhost:8000/docs.

Локально без Docker (нужны Postgres с pgvector и uv):

```bash
uv sync
uv run python -m mcp_server.server
uv run uvicorn api.main:app --reload --port 8000
```

Тесты на отдельной базе (её содержимое удаляется): `TEST_DATABASE_URL=postgresql://assistant:assistant@localhost:5432/assistant_test uv run pytest`.

## Структура

```

```

## Для C: подключение агента к MCP

Адрес: `http://mcp:8001/mcp` внутри compose, `http://localhost:8001/mcp` снаружи. Транспорт — streamable HTTP.

```python
from langchain_mcp_adapters.client import MultiServerMCPClient

client = MultiServerMCPClient(
    {"events": {"url": "http://localhost:8001/mcp", "transport": "streamable_http"}}
)
tools = await client.get_tools()  # create_event, get_events, search_events
```

| Тул | Аргументы | Возвращает |
| --- | --- | --- |
| `create_event` | `user_id`, `event_type` (task / meeting / reminder), `name`, `description`, `start_at`, `duration_minutes` | событие + `conflicts` |
| `get_events` | `user_id`, `start_time`, `end_time`, `event_types`, `include_undated_tasks` | список событий по времени |
| `search_events` | `user_id`, `query`, `start_time`, `end_time`, `limit` | список с `score` и `matched_by` |
| `update_event` | `user_id`, `event_id`, `name`, `start_at`, `description`, `duration_minutes` | событие + `conflicts` |
| `complete_event` / `delete_event` | `user_id`, `event_id` | событие |
| `delete_events` | `user_id`, `event_types?`, `confirmed?` | список удалённых |

**Импорт календаря из CSV.** `POST /v1/events/import?user_id=…` с файлом (колонки `id`,
`date` в формате ГГГГ-ММ-ДД, `time` в ЧЧ:ММ, `text`). Строки сохраняются в ту же таблицу
`events`, что и созданные голосом, типом `task` с длительностью 60 минут — поэтому
импортированное событие занимает время и участвует в поиске пересечений. Повторная
загрузка того же файла дублей не создаёт: пара (`user_id`, `external_id` из колонки `id`)
уникальна. Эмбеддинги на импорте не считаются (на 1000 строк это 1000 запросов к GigaChat),
поэтому такие события находятся полнотекстовым поиском, но не поиском по смыслу.
Тот же CSV можно просто прислать боту файлом в чат.

**Автоматические напоминания.** Бот раз в `REMINDER_INTERVAL_SECONDS` (30 с) забирает из базы
активные события, у которых `start_at` наступил, а `notified_at` пуст, отправляет их в MAX и
в том же запросе проставляет отметку — повторно после перезапуска сервиса они не придут.
`REMINDER_LOOKBACK_MINUTES` (60) ограничивает «догоняющие» отправки: после долгого простоя
пользователь получит только недавнее, а не прошлогодние даты из импортированного календаря.
Если отправка не удалась, отметка снимается и попытка повторится в следующий тик.

`delete_events` — массовое удаление («удали все задачи»): без `confirmed=true` ничего не
удаляет и отвечает ошибкой с числом записей, агент спрашивает подтверждение. Один вызов вместо
цикла по `delete_event`, иначе на 6+ записей не хватает шагов агента.

**Длительность и пересечения.** Для встречи через MCP `duration_minutes` обязателен:
`create_event` без него отвечает ошибкой «спроси, сколько продлится» и ничего не сохраняет
(если пользователь не знает — агент передаёт 60 и говорит об этом). В схеме и HTTP API поле
по-прежнему необязательно: старая встреча без длительности считается часовой. Дело без
длительности время не занимает (это срок: «сдать отчёт до 18:00»), у напоминания длительности
нет. В ответе у события есть `end_at` — конец занятого времени (`null`, если время не занято).
Если новая или перенесённая запись пересекается с активными встречами или делами с
длительностью, она **всё равно сохраняется**, а пересечения приходят в `conflicts` — агент
предупреждает пользователя и предлагает перенести. Встык (15:00–16:00 и 16:00) — не пересечение.

Что важно для агента:

- **`user_id` — в каждом туле.** Агент подставляет его сам из запроса бота, LLM его не придумывает. Надёжнее всего привязать его к тулам в коде агента, а не просить модель.
- **Даты** — ISO 8601 со смещением. Время без смещения трактуется как московское.
- **Период — полуинтервал** `[start_time, end_time)`: «сегодня» = с 00:00 сегодня до 00:00 завтра.
- **Ошибки возвращаются текстом, понятным LLM:** «Для типа 'meeting' нужно указать дату и время», «Время … уже прошло (сейчас …)». На такую ошибку агент должен задать уточняющий вопрос, а не падать.
- **В ответе есть `weekday`** («пятница»): модель часто ошибается, вычисляя день недели сама.
- **`search_events.query`** — суть без служебных слов: «договор», а не «найди задачу про договор» (лишние слова тоже не ломают поиск, но мешают нечёткому совпадению).
- **Лимит поиска** — до 50 записей, по умолчанию 50 с периодом и 10 без периода.
  Даже поиск с периодом не гарантирует полный список. Для точного списка и подсчёта
  записей за период используйте `get_events`. Верхняя граница поиска также исключается:
  «по 30 октября» означает `end_time` = 31 октября 00:00.

Отличия от доски Miro: `get_event` → `get_events`, `get_event_by_query` → `search_events`, во все тулы добавлен `user_id`, поле `datetime` называется `start_at`.

## Для D: HTTP API

| Метод | Что делает |
| --- | --- |
| `GET /v1/events?user_id&from&to&type&include_undated` | события за период; `type` можно повторять |
| `GET /v1/events/search?user_id&q&limit&type` | поиск; повторяемый `type` фильтрует до ограничения выдачи |
| `GET /v1/events/{id}/ics?user_id` | файл .ics для кнопки «Добавить в календарь»; 409 у задачи без даты |

Формат события — модель `Event` в `common/schemas.py`, полная схема — в `/docs`.

## Решения (для README и презентации)

- **Поиск из трёх сигналов, склеенных через Reciprocal Rank Fusion.** Полнотекстовый по-русски (словоформы: «договору» → «договор»), триграммы (опечатки: «презинтация»), эмбеддинги GigaChat в pgvector (смысл: «слайды» → «презентация»). Оценки этих способов несравнимы, а места в выдаче сравнимы, поэтому RRF без подбора весов. В ответе видно, какой способ нашёл запись (`matched_by`).
- **Слова запроса через ИЛИ, а не И.** Иначе «задачу про договор» не находит «Подписать договор».
- **Деградация вместо ошибки.** Нет ключа GigaChat или он недоступен — событие сохраняется без эмбеддинга, поиск работает по тексту.
- **Правила данных в двух местах.** Встреча и напоминание без времени запрещены и в Pydantic (понятная ошибка для LLM), и CHECK-ограничением в БД (защита от любого кода).
- **Время в UTC в базе, наружу — в часовом поясе пользователя.** Агенту не нужно пересчитывать.
- **Один `EventRepository` со всем SQL.** MCP и API — тонкие обёртки над ним, логика не дублируется.
- **asyncpg и сырой SQL вместо ORM.** Поиск — это CTE с tsvector, trigram и pgvector, в ORM он читался бы хуже.
- **Пересечение — предупреждение, а не запрет.** Человек может осознанно поставить встречи
  внахлёст; молча отказать хуже, чем сохранить и спросить «перенести?». Пересечения ищутся
  одним запросом по индексу `(user_id, start_at)`: полуинтервалы `[start, end)`, а условие
  «началась не раньше суток назад» отсекает лишнее (запись не длится дольше суток).
- **Длительность хранится, только если её назвали.** `NULL` значит «по умолчанию для типа» —
  так видно, где время сказал пользователь, а где подставили мы.

## Обновление базы

Compose запускает сервис `migrate` до API/MCP. Он применяет новые файлы из
`db/migrations` транзакционно и записывает версии в `schema_migrations`.
Существующие события сохраняются. Без Compose:

```bash
uv run python -m scripts.migrate
```

## Что улучшить при наличии времени

- Mini App уже использует проверку подписанного `X-Max-Init-Data`; переданный
  `user_id` обязан совпадать с проверенным. Режим разработки включается отдельно
  через `API_ALLOW_DEV_USER_ID=true` и выключен по умолчанию.
- Часовой пояс на пользователя, а не один на всех.
- Фоновая догрузка эмбеддингов для записей, сохранённых при недоступном GigaChat.

Семантический поиск дополнительно проверяет кандидатов через GigaChat: близость
векторов сама по себе не подтверждает совпадение темы. На проверку передаются только
названия и типы, одинаковые кандидаты объединяются. При отказе проверки остаются
только текстовые/нечёткие совпадения; неподтверждённые семантические результаты
не выдаются. Фильтр типов применяется в SQL до ранжирования и лимита.
