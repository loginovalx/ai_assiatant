# MAX bot (Python 3.12) — transport layer для голосового ассистента

**Зона ответственности B / папка `bot/`** согласно командному плану. Бот **не** извлекает даты, не пишет напрямую в PostgreSQL и не вызывает MCP. Только MAX → ASR → Agent API → MAX. Анализ текста, контекст уточнений и работа с задачами принадлежат сервису `agent/` (C).

## Что работает в этом каркасе

- Текст MAX → `POST /v1/agent/message` → текстовый ответ.
- Голос MAX (`audio`, а также аудиофайл) → (готовая транскрипция MAX, если есть; иначе скачивание вложения и ASR) → текст → тот же Agent API → ответ.
- ASR заменяется настройкой: `whisper` (реальное распознавание речи локально), `http` (адаптер под совместимый HTTP ASR), `disabled` (только если сам MAX передал готовую транскрипцию). Байты аудио **не перекодируются**.
- Redis FSM `idle → recognizing → thinking → idle` с TTL 5 минут и защитой от одновременных запросов одного пользователя; после рестарта `bot:state:*` сбрасываются.
- «Голос получил, распознаю…», «Распознал: … Думаю…», ответ; дружелюбные сообщения об ошибках; игнорирование сообщений ботов, дублей и групповых чатов.
- Транспорт — **вебхук** (`bot/webhook.py`, FastAPI): `uvicorn bot.webhook:app`, маршрут `POST /webhook`, проверка подписи заголовком `X-Max-Bot-Api-Secret` (`MAX_WEBHOOK_SECRET`). Подписку регистрирует `bot/subscribe.py`.
- **Автонапоминания** (`bot/reminders.py`): фоновая задача раз в 30 секунд забирает из базы наступившие события и сама шлёт «Напоминание: …» в MAX. Источник истины — таблица `events` (колонка `notified_at`), поэтому перезапуск сервиса напоминания не теряет и не дублирует.
- **Загрузка календаря**: CSV-файл (`id,date,time,text`), присланный боту в чат, разбирается и сохраняется в общий календарь пользователя. Тот же импорт доступен через `POST /v1/events/import` у HTTP API.
- **Приветствие** при первом контакте (`bot_started`, `/start`, `/help` или первое сообщение незнакомого пользователя) — один раз, флаг `bot:greeted:*` в Redis.

> **Не проверено на реальном MAX в этом окружении:** для этого нужен `MAX_TOKEN` и живой доступ к API; проект содержит автотесты на искусственных обновлениях. Развернутый публичный бот/прототип не создан этим архивом.

## Как получить MAX_TOKEN

При наличии верифицированного профиля MAX для партнёров: раздел **Чат-боты → Создать**, заполнить карточку и дождаться модерации; затем **Чат-боты → ⋮ → Настройки → скопировать токен**. Официальная инструкция: https://dev.max.ru/docs/chatbots/bots-create/create . Если коллега уже зарегистрировал бота, попросите у него **доступ через защищённый канал**, не публикуйте токен в GitHub. Если в MAX бот не создаётся из-за ограничений аккаунта, локальные тесты всё равно можно разрабатывать без токена — тулзы в `bot/` импортируются и поднимаются без реального MAX (см. `/health`).

## Запуск: вместе с остальным проектом (Docker Compose)

`bot` — один из сервисов корневого `docker-compose.yml`, отдельного compose-файла для него нет.

```bash
cp .env.example .env
# заполнить MAX_TOKEN и MAX_WEBHOOK_SECRET (любая случайная строка 5-256 символов)
docker compose up --build bot   # или без аргумента — поднимет весь стек
```

Слушает `:8080` (`/health`, `/webhook`), ходит в `agent` и `redis` по именам сервисов в сети compose.
**MAX принимает вебхук только по HTTPS на порту 443 с доверенным сертификатом** — локальный
`:8080` сам по себе снаружи не виден. Для теста с реальным MAX нужен обратный прокси с
сертификатом или временный туннель (например `cloudflared`) перед этим портом, и затем:

```bash
docker compose exec bot python -m bot.subscribe add https://ваш-домен/webhook
```

### Подтверждение доставки

MAX требует HTTP 200 в течение 30 секунд; при тайм-ауте или другом статусе повторяет
доставку с увеличивающимися интервалами (60, 150, 375 секунд и далее), до 10 попыток
в течение 8 часов ([официальная политика Webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions)).
Обработчик ждёт до 25 секунд. Если запрос ещё выполняется, endpoint отвечает HTTP 503,
но задача продолжает работу. Повтор, пришедший в это время, тоже получает 503; после
завершения он получает 200. При остановке приложения активные задачи отменяются.

Для `message_created` Redis хранит отдельные ключи: активная обработка арендуется на
5 минут, а завершённый MAX `mid` помечается на 24 часа. Падение процесса оставляет только
истекающую аренду. Если агент уже записал изменение, но бот упал до отметки завершения,
повтор использует тот же `request_id` из user ID и MAX `mid`; Agent API возвращает
сохранённый receipt и не создаёт запись второй раз.

### Запуск long-polling без Docker и туннеля (проще всего локально)

Вебхуку нужен публичный HTTPS-адрес; long-polling обходится без него — бот сам забирает
обновления из MAX API (`GET /updates`), код обработки тот же (`bot/handler.py`):

```bash
set -a; source .env; set +a   # в .env достаточно MAX_TOKEN, REDIS_URL, AGENT_URL
python -m bot.polling
```

Курсор `marker` хранится в Redis (`bot:updates:marker`): после рестарта старые обновления
не приходят повторно, а накопившиеся за простой — приходят. Тем же процессом поднимается
планировщик напоминаний (`bot/reminders.py`).

**Первое голосовое** с `ASR_PROVIDER=whisper` (по умолчанию) скачает модель Whisper — нужен
интернет и немного времени на первый запрос. Нет доступа — поставьте `ASR_PROVIDER=http` со
своим ASR или `ASR_PROVIDER=disabled` (тогда голос обрабатывается только если его текст уже
прислал сам MAX в `payload.transcription`).

## Локальный запуск без Docker (Python 3.12, uv)

```bash
uv sync --group bot --group dev
cp .env.example .env
# Заполнить MAX_TOKEN и MAX_WEBHOOK_SECRET, запустить Redis на localhost:6379
# .env автоматически не загружается: экспортируйте переменные:
set -a; source .env; set +a

uv run uvicorn bot.webhook:app --host 127.0.0.1 --port 8080 --reload
```

`AGENT_URL` по умолчанию `http://localhost:8001` (см. `bot/config.py`) — укажите реальный адрес
сервиса `agent/` (локально обычно `:8002`, см. `agent/README.md`).

## Agent API: строго по командному контракту

Бот отправляет:

```http
POST /v1/agent/message
Content-Type: application/json

{"user_id":"123456789","text":"Напомни завтра позвонить Ивану"}
```

Ожидает:

```json
{"reply_text":"Уточни время напоминания", "status":"need_clarification", "events":[]}
```

`status` может быть `done`, `need_clarification`, `needs_confirmation`, `error`.
Для голосового изменения бот передаёт `confirm_changes=true`: агент возвращает
`needs_confirmation` и `draft`, а запись выполняется через `POST /v1/agent/confirm`
после кнопки или ответа «да». Повторное подтверждение того же создания использует
ID черновика и возвращает уже сохранённое событие. При ошибке черновик остаётся для повтора.
Контекст уточнений живёт в Redis `agent:ctx:<id>`, а `bot:state:<id>` содержит
временную фазу и ID текущего запроса, а не историю диалога.

## ASR и голосовые

1. `MAX` отправляет update `message_created` с вложением `type=audio`, `payload.url` (иногда в аудио доступен `payload.transcription`). Если транскрипция есть, она переиспользуется.
2. Бот загружает URL аудио с MAX CDN, ограничивая загрузку 15 МБ и проверяя HTTPS+домен.
3. `ASR_PROVIDER=whisper` — `faster-whisper` с русским языком и CPU `int8`, модель `base`. Не требует платного API; требует загрузки весов и времени CPU. Форматы OGG/Opus/MP3 декодируются внутри PyAV.
4. `ASR_PROVIDER=http` — `POST ASR_HTTP_URL` как multipart `file`, ожидаемый JSON `{"text":"..."}`. При `ASR_HTTP_TOKEN` добавляется `Authorization: Bearer ...`. **Коммерческие платформы имеют собственные контракты**: при выборе конкретного ASR исследователем реализуйте соответствующий адаптер в `bot/asr.py`.

## FSM

```text
idle (нет ключа в Redis)
    │ пришёл текст            │ пришёл голос
    ▼                        ▼
 thinking                 recognizing
    │                        │ ASR вернул текст
    │                        ▼
    │                     thinking
    └─────────────┬──────────┘
                  │ success/error/finally
                  ▼
                 idle
```

Redis `SET NX EX` защищает от повторной обработки сообщения до окончания текущего запроса. `bot:state:{user_id} = "thinking:<request_id>"` или `"recognizing:<request_id>"`, TTL 300 секунд; переход и освобождение выполняются атомарно. Если пользователь отправит ещё одно сообщение до завершения, бот скажет «Ещё думаю над прошлым запросом». TTL предотвращает вечную блокировку. При старте очищаются **только** ключи `bot:state:*` (не `agent:ctx:*`). Сброс безопасен в предположении одного экземпляра бота.

## Тесты и стиль

`dev` — группа по умолчанию (`uv sync` её уже ставит), отдельно подключать не нужно:

```bash
uv run pytest -q
uv run ruff check bot tests
uv run ruff format --check bot tests
```

Тесты проверяют текстовый и голосовой маршрут, использование транскрипции MAX, занятость пользователя, состояние после ошибок, отдельные сессии, дубликаты, группы, форму запросов к MAX и URL аудио. Тесты используют фейки; реальный сценарий проверяется отдельно с токеном в MAX.

## Особенности MAX API

- Используется `https://platform-api2.max.ru` и **сырой токен** в `Authorization` (не `Bearer`). По документации MAX для HTTPS может понадобиться добавить сертификат Минцифры в доверенные сертификаты вашей системы/контейнера; не отключайте TLS-проверку.
- Транспорт — вебхук, не Long Polling: `bot/subscribe.py` регистрирует `POST /subscriptions`
  с `url` (обязательно HTTPS, порт 443, путь `/webhook`) и секретом; MAX сам шлёт обновления на
  этот адрес. Активная webhook-подписка не совмещается с Long Polling на одном боте.
- `POST /messages?chat_id=...` (если в диалоге `chat_id` отсутствует — `?user_id=...`) с телом `{"text": "..."}`. Вложения с аудио скачиваются по `payload.url`.
- На отправке соблюдается ограничение ~2 сообщения/сек в один диалог; для ответа можно использовать `user_id`, если `chat_id` в update равен `null`.
- По соображениям приватности личный ассистент обслуживает только чаты типа `dialog`.

Официальная документация: https://dev.max.ru/docs-api/methods/GET/updates/ ; https://dev.max.ru/docs-api/methods/POST/messages ; https://dev.max.ru/docs-api/objects/Update/

## Интеграция с монорепозиторием

Уже сделано: `bot` — сервис корневого `docker-compose.yml` (общий `infra/Dockerfile`,
`args: {GROUP: bot}`), зависимости в `pyproject.toml` (группа `bot`), `AGENT_URL` внутри
compose-сети указывает на реальный `agent`, не на мок. `bot/models.py` — копия контракта из
`common/schemas.py` (`AgentRequest`/`AgentResponse`); если контракт поменяется, поправить
в обоих местах.
