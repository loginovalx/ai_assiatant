# Агент

Понимает запрос пользователя, вызывает MCP-тулы через GigaChat и формулирует ответ.
LLM подключена через [gpt2giga](https://github.com/ai-forever/gpt2giga): это прокси, который
делает GigaChat совместимым с OpenAI API, поэтому агент написан на обычной библиотеке `openai`.

## Запуск

```bash
cp .env.example .env   # заполнить GIGACHAT_CREDENTIALS и LLM_API_KEY
docker compose up --build
```

Агент: http://localhost:8002, документация: http://localhost:8002/docs.

Без Docker: поднять gpt2giga и MCP, затем `uv run uvicorn agent.main:app --port 8002`.

## Для бота (B): контракт

```
POST /v1/agent/message
{"user_id":"123", "text":"Напомни завтра в 10 позвонить Ивану",
 "request_id":"d3fc39af-c74c-47c3-b03a-7cc5898f1575", "confirm_changes":false}
→ 200 {"reply_text":"...", "status":"done" | "need_clarification" | "needs_confirmation" | "error",
       "events":[...], "draft":...}

POST /v1/agent/confirm   {"user_id":"123", "draft":...} → сохранение подтверждённого черновика

POST /v1/agent/reset     {"user_id": "123"}   → 204, очищает историю диалога
```

- Ответ всегда 200, даже если GigaChat упал: тогда `status = "error"` и вежливый `reply_text`.
  Боту достаточно показать `reply_text`.
- `need_clarification` — агент задал вопрос («На какое время?»). Следующее сообщение
  пользователя просто отправляйте тем же запросом: агент помнит контекст.
- Голос: бот сначала распознаёт речь, потом отправляет текст сюда.
- Для голоса передайте `confirm_changes=true`: изменения проходят dry-run и возвращаются
  как `needs_confirmation` с `draft`. После явного согласия передайте тот же черновик в `/confirm`.
- `request_id` — UUID одного сообщения. При сетевом повторе сохраните тот же ID и тело запроса.
  Повтор возвращает сохранённый результат, а создание после потерянного ответа MCP защищено
  тем же ключом в PostgreSQL. Разным сообщениям нужны разные ID, даже если текст совпал.
- Запросы одного пользователя сериализуются через Redis; повтор того же запроса ждёт результат,
  другой запрос получает понятный ответ о занятости. Сброс не обгоняет выполняющийся запрос
  (HTTP 409); недоступный Redis при сбросе даёт 503.
- Ответ обычно занимает 5–20 секунд. Общий лимит — 65 секунд (`AGENT_REQUEST_TIMEOUT_SECONDS`),
  таймаут клиента бота — 75 секунд. Для нестандартного лимита сервера согласуйте таймаут клиента.
- Модели — `AgentRequest` / `AgentResponse` в `common/schemas.py`.

## Как устроен

```
бот ──HTTP──▶ agent/main.py ──▶ agent/core.py (цикл)
                                   │  ├─ prompt.py  — системный промпт с временем и календарём
                                   │  ├─ memory.py  — история в Redis
                                   │  └─ tools.py   — MCP ⇄ формат тулов OpenAI
                                   ├──▶ gpt2giga ──▶ GigaChat
                                   └──▶ MCP-сервер ──▶ PostgreSQL
```

Цикл на один запрос: LLM видит промпт, историю и тулы → просит вызвать тул → агент вызывает
его на MCP → отдаёт результат LLM → … → LLM пишет текстовый ответ. Максимум 6 раундов.

## Решения

- **Тулы берутся с MCP-сервера, а не описываются заново.** Единственный источник описаний —
  `mcp_server/server.py`. По дороге схема упрощается до подмножества JSON Schema, которое
  стабильно понимает GigaChat (без `anyOf`, `additionalProperties`).
- **`user_id` скрыт от модели.** Его нет в схеме тулов, агент подставляет его сам и
  перезаписывает, даже если модель прислала свой. Пользователь не может уговорить модель
  показать чужие задачи.
- **Уточнение — отдельный тул `ask_user`.** Явный сигнал надёжнее, чем угадывать по знаку
  вопроса. Бот получает `status = need_clarification`.
- **В промпте — календарь на 14 дней.** LLM плохо считает «в следующую среду»,
  а по готовой таблице «дата — день недели» почти не ошибается. Плюс правила по умолчанию:
  «в 3» = 15:00, срок дела без часа = 18:00. Части дня без часа требуют уточнения.
- **Ошибки тулов возвращаются модели.** «Для встречи нужно указать время» — модель
  исправляется или спрашивает пользователя, а не падает.
- **В историю пишем только реплики, без вызовов тулов.** Обрезка списка не разрывает пары
  «вызов → результат», а к ответу ассистента дописывается скрытая сводка записей с id —
  чтобы «перенеси её на завтра» знало, о какой записи речь.
- **История — последние 10 реплик, TTL 7 дней** (`agent:ctx:{user_id}`). После ошибки
  обмен не сохраняется, повтор начинается с чистого листа.
- **При уточнении сохраняется исходная просьба.** Ответ «один час» дополняет ранее
  названное время встречи. Дословный контекст для проверки времени передаёт агент;
  модель не может подменить его своим `user_text`. Служебные данные уточнения в
  сообщения LLM не попадают; после завершённого действия контекст уточнения очищается.
- **Результаты тулов сжимаются** (без `user_id` и служебных дат) — меньше токенов, быстрее ответ.
- **Ответы со списком и поиском формируются по полям БД.** Дата, день недели, время,
  длительность и название не переписываются моделью. Поисковая выдача обозначается
  как выборка по релевантности. Если модель недоступна после успешного чтения,
  найденные записи всё равно возвращаются.
- **Пересечения встреч — предупреждение.** `create_event`/`update_event` сохраняют запись и
  возвращают `conflicts`; по промпту модель говорит «Учтите: в это время уже есть …, перенести?»
  и ничего не переносит сама. Пересекающиеся записи попадают в скрытую сводку, поэтому
  «перенеси ту встречу» следующим сообщением знает её id.
- **Длительность встречи — спрашиваем.** «На полчаса», «с 15 до 17» → `duration_minutes`.
  Не назвали — `ask_user` («Сколько продлится встреча?», или вместе со временем одним
  вопросом). «Не знаю / не важно» → 60 и в ответе «поставил на час, если нужно — поменяю».
  Если модель забыла спросить, `create_event` сам откажет с этой подсказкой — встреча
  без длительности молча не создаётся. У дела длительность только названная.
- **Час не выдумываем.** «Завтра», «в пятницу» без часа — повод для `ask_user`, а не для
  10:00 «по умолчанию». «Утром/вечером» тоже требует часа. «Полдень» и «полночь» —
  точное время; «через полчаса» — относительное. Если модель ошиблась в числе для
  простого «в понедельник», дата вычисляется по серверному календарю. Явно названные
  даты и неоднозначные периоды автоматически не сдвигаются: противоречие с днём недели
  требует уточнения. Срок «до пятницы» → 18:00 — только для дел.
- **Длительность у «напомни» → дело.** У напоминания длительности не бывает, но терять
  названные «два часа» нельзя: `create_event` отказывает с подсказкой создать `task`,
  модель пересоздаёт запись делом и объясняет это пользователю.
- **Про данные отвечаем по полям.** `description` — исходная фраза пользователя, в ней
  может быть то, чего в записи нет (живой GigaChat на вопрос о длительности напоминания
  пересказывал фразу: «с 10:00 до 12:00» при пустом `duration_minutes`). Время и
  длительность — только из `start_at`, `end_at`, `duration_minutes`.

## Тесты

`tests/test_agent.py`: скриптованная LLM + настоящие MCP, Postgres и Redis. Проверяют логику
вокруг модели: подстановку `user_id`, уточнения, ошибки тулов, историю, лимит шагов, HTTP.
Качество понимания запросов проверяется отдельным прогоном на настоящем GigaChat.

```bash
TEST_DATABASE_URL=... TEST_REDIS_URL=redis://localhost:6379/15 uv run pytest tests/test_agent.py
```

## Воспроизводимая оценка качества

`scripts.evaluate_agent` читает CSV с колонками `id`, `text`, `expected_action`,
`expected_fields`, `reference_now`, `user_id`, `dialogue_history`, `seed_ids`.
Поля ожиданий, истории и ID содержат JSON. Используются отдельные ресурсы,
уникальные пользователи и очистка только записей текущего кейса:

```bash
EVAL_DATABASE_URL=postgresql://assistant:assistant@localhost:5432/assistant_eval \
EVAL_REDIS_URL=redis://localhost:6379/14 \
uv run python -m scripts.evaluate_agent /path/to/Dataset.csv --output /tmp/evaluation.json
```

Время агента и проверки MCP фиксируются по `reference_now` каждого кейса; даты не
сдвигаются относительно дня запуска. Создания сверяются с фактическими строками БД;
списки и поиск — с ID, типами и границами периода. Дополнительный вопрос о длительности
встречи допускает ответ «Один час» и отражается в отчёте. Заголовки сравниваются строго
после нормализации регистра и пунктуации, поэтому смысловые перефразирования могут
получать отрицательную оценку и требуют ручного просмотра.

Для запросов к существующим записям передайте `--seeds /path/to/events.json`: массив
исходных событий с логическими `id` из эталона, `user_id`, `type`, `name`, `start_at`,
необязательными `description`, `duration_minutes`, `status`. Записи чужого владельца
сохраняются отдельно. Отсутствующие эталонные события не выдумываются: такие кейсы
отмечаются `unverified`, отдельно от ошибок и успешных проверок. Код возврата 0 означает
полное покрытие переданного набора и ≥90% успеха, 2 — ошибки или неполное покрытие.
Отчёт содержит модель, хеши исходников/датасета и фактические результаты; не публикуйте
в нём рабочие пользовательские данные без необходимости.

Для календаря с колонками `id,date,time,text` есть самостоятельная проверка чтения:

```bash
EVAL_DATABASE_URL=postgresql://assistant:assistant@localhost:5432/assistant_eval \
EVAL_REDIS_URL=redis://localhost:6379/14 \
uv run python -m scripts.check_calendar /path/to/calendar.csv \
  --reference-time 2026-10-30T09:00:00+03:00 --output /tmp/calendar-check.json
```

Нужны работающий LLM-прокси и `GIGACHAT_CREDENTIALS` для индексации: названия записей
передаются провайдеру эмбеддингов, запросы и результаты — провайдеру LLM. Ожидания
вычисляются из исходных дат и ID: 20 списков за периоды и до 20 поисковых запросов
по редким названиям и их вариантам. Списки сравниваются целиком; поиск проверяет
наличие обязательных ID, а не точность всех рекомендаций. Дополнительно проверяются
изоляция владельцев и отсутствие изменений календаря при чтении. Записи временных
пользователей удаляются после прогона; бот MAX не запускается. Код возврата 0 означает
успех всех 40 проверок (либо всех явно выбранных через `--only`); 2 — недостаточное
покрытие, если календарь содержит меньше десяти редких названий. Отчёт содержит
исходные пользовательские данные.
