# Учёт расхода API

`common/usage.py` собирает счётчики из ответов провайдера для каждого вызова агента,
классификатора релевантности и эмбеддингов. В записи нет текста, user_id, названий,
ключей или векторов. Счётчик выводится в журнал `token_usage`; необязательный
`USAGE_LOG_PATH` добавляет JSONL в приватный файл. Каталог должен существовать и быть
доступен сервису. Файл не хранится в Git. В Compose для постоянного файла нужен
приватный bind mount; путь внутри контейнера сам по себе не сохраняется при пересоздании.
Собирайте данные со всех сервисов: agent, mcp, api и bot (он индексирует загруженные CSV).

## Семантика токенов

- `completion_tokens` — фактически сгенерированные токены, включая параметры вызова
  инструмента. Это не лимит ответа и не размер итогового сообщения MAX. Агент не задаёт
  `max_tokens`; при использовании прокси нужно отдельно проверять его настройки.
- `finish_reason` показывает причину завершения ответа. `length` означает обрезание по
  лимиту. Агент отклоняет такой результат до вызова инструмента. `null` означает, что
  провайдер не сообщил распознаваемую причину завершения.
- Прямой GigaChat: `total_tokens` уже содержит тарифицируемый объём; повторно вычитать
  `precached_prompt_tokens` нельзя.
- Используемый `gpt2giga` прибавляет кэшированные токены обратно в OpenAI `total_tokens`;
  поэтому для этого источника `billable_tokens = total_tokens - cached_tokens`.
  При обновлении прокси проверьте его конвертацию usage и тесты учёта.
- Для Embeddings складывается `usage.prompt_tokens` всех элементов ответа.
- Отсутствие счётчика — `null`, а не ноль. После тайм-аута неизвестно, списал ли
  провайдер токены. Отчёт помечает неполный замер и не строит точный месячный прогноз.
- SDK может повторить транспортный запрос внутри одного вызова; его промежуточные
  списания не видны. Для окончательной сверки нужен личный кабинет/выгрузка провайдера.

Описание полей: [GigaChat usage](https://developers.sber.ru/docs/ru/gigachat/api/grpc/grpc-methods).

## Расчёт

Сначала запишите число реально выполненных пользовательских запросов. Подтверждение
черновика не вызывает LLM; сохранение события может вызвать эмбеддинги. Не смешивайте
импорт/первичную индексацию календаря и обычные пользовательские обращения.

Простое одиночное изменение после успешной записи больше не вызывает LLM только
для формулировки подтверждения: ответ, пересечения и ссылки на записи строит код.
Составные просьбы и исправление ошибок инструментов сохраняют полный цикл.
Голосовой предпросмотр и подтверждение работают как раньше. Правила промпта, число
реплик истории и размер выдачи не сокращены.

Агент передаёт стабильный `X-Session-ID` отдельно для каждого пользователя и модели —
HMAC от внутреннего ID и модели с ключом `LLM_API_KEY`, без передачи открытого MAX ID в заголовке.
При ротации ключа идентификатор меняется. Используемая версия `gpt2giga:0.3.1a1`
передаёт этот заголовок GigaChat. Постоянные инструкции стоят в начале промпта,
изменяющееся текущее время и календарь — в конце. Это повышает возможность повторного
использования префикса, но не гарантирует попадания в краткоживущий кэш провайдера.
Не включайте для этого conversation stitching: история уже передаётся агентом явно.

Сравнивайте одинаковые сценарии до и после обновления: число `operation=agent`,
сумму `billable_tokens`, долю `cached_tokens` во входе, ошибки и фактические записи
в календаре. Считайте отдельно простое действие, уточнение, поиск с изменением и
голосовое подтверждение. Рост доли кэша при неизменной сумме оплаченных токенов сам
по себе не доказывает экономию. Документация: [кэш GigaChat](https://developers.sber.ru/docs/ru/gigachat/guides/keeping-context),
[передача X-Session-ID](https://ai-forever.github.io/gpt2giga/prompt-caching/).

```bash
uv run python -m scripts.usage_report /private/usage.jsonl \
  --chat-rub-per-million 650 --embedding-rub-per-million 14 \
  --requests 100 --monthly-requests 3000
```

Число `100` здесь — пример: замените реальным объёмом замера. Тарифы задаются явно.
Один плоский тариф допустим только для журнала с одной разговорной моделью.
При маршрутизации Pro/Max задайте отдельные ставки для каждой модели:

```bash
uv run python -m scripts.usage_report /private/usage.jsonl \
  --model-rate GigaChat-2-Pro=500 --model-rate GigaChat-2-Max=650 \
  --embedding-rub-per-million 14 --requests 100 --monthly-requests 3000
```

Ставки в примере замените тарифами своего договора. CLI суммирует расходы агента и
классификатора поиска по фактическим моделям; неизвестная ставка вызывает ошибку.
Версия в имени вида `GigaChat-2-Pro:version` использует ставку базовой модели, если
не задана отдельная ставка для этой версии. Неизмеренный вызов остаётся неизвестным,
а месячный прогноз не строится. Не смешивайте `--chat-rub-per-million` и `--model-rate`.

После установки маршрутизации сравните качество, суммарные расходы на одну реальную
команду и частоту `reason=fallback_...`. Такой переход оплачивает вызовы обеих моделей,
поэтому большая доля переходов может съесть экономию. Количество строк `token_usage`
не равно числу пользовательских команд. Журнал `model_route` показывает выбор без
добавления платного запроса на оценку сложности. Переключение модели само по себе
не сокращает контекст; кэш и стоимость нужно измерять отдельно для Pro и Max.

Для действующих юридических клиентов GigaChat опубликованы синхронные ставки Max
650 ₽/млн и Embeddings 14 ₽/млн, с НДС. Для части договоров действует минимальный платёж
600 ₽ за месяц использования. Для новых клиентов с 1 сентября 2026 используется
Cloud.ru с отдельными тарифами. Значение `GIGACHAT_SCOPE=B2B` само по себе не доказывает
тариф конкретного аккаунта. Проверено 5 ноября 2026: [официальные тарифы](https://developers.sber.ru/docs/ru/gigachat/tariffs/legal-tariffs).

Полная месячная себестоимость: хостинг + БД/диск/резервные копии + API по замеру
(с учётом минимального платежа по договору) + платное ASR, если используется,
+ мониторинг/сопровождение.

Локальный Whisper не списывает токены GigaChat, но потребляет CPU/RAM. Бесплатный
пакет API не означает нулевую коммерческую себестоимость. Прогноз предполагает ту же
смесь сценариев и поведение кэша, что в замере. Клиентский счётчик не является выпиской
фактических денежных списаний аккаунта.
